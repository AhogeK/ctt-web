## 现行定稿（以用户原图**逐边量测**为准，2026-09-29 ✓）

**布局**：文案列在左（`lg:max-w-[42rem]` 的 h1 + **`max-w-[22rem]` 的窄栏段落（4 行）** + 按钮行）· 产品面在右并上提（**`lg:ml-[30%] lg:w-[68%] lg:-mt-[7rem]`**，实测 1440×1080 下 **783×524 @ [490,421→1273,945]**，其**左上角掖在文案下半身之下** ✓，右缘距容器 47px ✓）· 会话浮板 `right: 5rem` · **`bottom: calc(100% - 4.5rem)`（压进 72px）** · `width: min(22rem, 45%)`（352 ✓，左缘与文案留 25px ✓）。
**当前（用户引导第三步 ✓，已按用户纠正修因果 ✗✓）**：两卡**共用一层 3D 投影** —— `.hero-plane { transform: perspective(1200px) rotateY(-13deg); transform-origin: center center }`（**已删掉 `perspective-origin`** ✗：消融实测它对本元素是**空操作** ✓ —— 同视口下把该属性改回初始值，四角、两侧高度、局部缩放、浮板盒**全部读数不变** ✓，DPR=2 下同样不变 ✓），**≥1280px 生效** ✓；两卡自身 `transform: none` ✓ ⇒ 更准确的说法是"两卡作为**同一产品平面**的内容被**共同投影**" ✓。**实测**：大卡**左顶边比右顶边低 36px**（左下沉 / 右浮起 ✓）· **左右绘制高度比 1 : 1.15**（左窄右宽 ✓）· 绘制右缘 1293（视口 1440 ✓ 容器 1320 ✓）· 溢出 0 ✓ · **浮板沿中线真实压入 74px** ✓。
**局部缩放（比包围盒比更可信 ✓）**：卡左 x=551 **0.886×** · 中心 x=782 **0.974×** · 右 x=1036 **1.075×** ⇒ **左端文字按 89% 栅格化** ✓（`0.98` 是整体包围盒均值，**掩盖了左端**，不得用来证明"不糊" ✗）。
**为什么不是平面内旋转** ✓✓：`rotateZ` 只把两端沿同一条线平移，**两侧一样高** ⇒ 读成"歪"不是"浮" ✗（用户原话："**不是左边往下走右边往上走**" ✓）。下沉/浮起来自**投影除法**本身 ✓：`perspective(d)` 的消失点**就是 `transform-origin`** ✓（本例在中心）⇒ 远（左）半向原点收缩 ⇒ **顶边下落**、读成下沉；近（右）半背离原点扩张 ⇒ **顶边抬升**、读成浮起 ✓。**`perspective-origin` 不参与** ✗ —— 它只配 `perspective` **属性**、作用于**子元素**；这里是 `perspective()` **函数** ⇒ 消融实测为空操作 ✓（用户指出 ✓，实测确认 ✓）。
**<1280 保持轴对齐** ✓（实测：1024 溢出 +11px、1200 溢出 +29px ✗ ⇒ 该区间上透视会出横向滚动条 ✓；裁剪方案被否 —— section 盒宽仅 1200 ⇒ 会切掉右边框与圆角 ✗）。
**入场层次（用户："两张卡是一起出来的…先底部的大卡再顶部的小卡"）** ✓：大卡经平面包装层 `hero-fade-rise` + `[animation-delay:210ms]`（210→530ms ✓）；浮板加自身入场 `.hero-panel { animation: hero-fade-rise 320ms ease-out both }` + `[animation-delay:440ms]` ✓ —— 延迟期间 `both` 把它钉在 `from` 帧（透明 ✓）⇒ 两层不同时出现 ✓。**LCP 红线**：`h1` 是 `.hero-rise`（只位移、不透明 ✓），入场延迟不得加在它身上 ✓；全部动画在 `prefers-reduced-motion: no-preference` 门控内 ✓。
**量具事实（2026-09-29 连犯三次后立规 ✓）**：① 探针若注入 `position: static` 的卡片，其 `offsetParent` 是 `.hero-plane` ✗ ⇒ 未加 inset 时两者重合、**一加负 inset 口径就落到平面上** ✓ ⇒ 要量卡片外框须先给卡片 `position: relative` ✓。② 探针公式是 `-off - border` ⇒ `off=0` 时已在边框外 ✓（标签易反 ✗）。③ 跨档数据不可并列 ✗（48% 档 `670×527` vs 54% 档 `752` ✗）⇒ 每次采集带档位与元素标识 ✓。
**border-box 口径 + 约束层（第二轮复核 ✓✓）**：① 旧探针量的是 **padding-box**（相对元素自身包含块 ✓）⇒ 负 inset 探针取 **border-box**：大卡左/右竖边 **454.90 / 625.74**（比 1.376）、小卡 **247.50 / 287.51**（比 1.162、Δy −70.20）；两套序列**并列不覆盖** ✓。② `getBoundingClientRect()` 只给**轴对齐外接矩形** ✗，不能在屏幕坐标直接加减边框宽 ✓。③ 绝对定位包含块是**两级**：浮板的 `45%` 相对**平面** ✓，浮板内探针相对**浮板自身** ✓。④ **内容宽约束层 = `.hero-viewport` 的 `max-w-[1200px]`** ✓（`section.hero-handoff` 是全宽、无 max-width ✗ ⇒ 在它上面注入无效 = 量具失误 ✓）；放宽到 1360 ⇒ 列宽 **714→813**、段落→大卡间距 **92→160px** ✓。
**口径更正（专家复核 + 本侧实测 ✓✓）**：① **小卡不是 352 宽** ✗ —— `width: min(22rem, 45%)` 实际取 **45% × 714 = 321.3** ✓（`22rem=352` 未生效）；border-box **321.391**、`offsetWidth 321 × 252`，而**四角探针量到的是 padding-box 319.37**（差两个 1px 边框 ✓，`offsetParent = hero-plane` ✓）；按真实平面坐标复算小卡 ⇒ 上/下边 −11.59/−5.08、Δy −69.60、比 1.161 ✓（若按 352 代入会得到 −78.1/1.180 ✗ 与实测不符 ✓）。② **`−1/m34` 不是真实视距** ✗：组合矩阵 `M=P(d)·R_y(−θ)` 的 `m34=−cosθ/d`、`m14=−sinθ/d` ✓ ⇒ `−1/m34 = d/cosθ`（实测 736.05 = 700/cos18° ✓），正确反解 `d=1/√(m14²+m34²)` = **700.03** ✓ ⇒ 先前"偏差待解释"是**误报** ✗✓。③ `Δy` 应带符号：`Δy_top = −(H/2)(k_near−k_far)` ✓；先前"1200 档偏高 9%"是我代入错误 ✗ ⇒ 五档闭式复算与实测**逐档一致** ✓。
**投影形状** ✓✓（像素探针实测，括号内为矩阵推算值，两者差 0.06°）：大卡上边 **−2.88°**（−2.82）/ 下边 **+2.88°**（+2.82）· 左右高度 **487.2 / 564.2**（比 **1.158**）；小卡上边 **−4.87°**（−4.74）/ 下边 **−2.10°**（−2.04）· 左右高度 **248.5 / 265.9**（比 1.070）· 上下**斜率差 −2.77°**。

## 硬规则（每条都付过学费）

1. **下沉 / 浮起只能靠投影除法，不能靠 `rotateZ` 也不能靠 `perspective-origin`** ✓✓ —— `rotateZ` 两侧等高 ⇒ 只读成"歪" ✗；`perspective-origin` 对 `perspective()` **函数**无效 ✗（消融：改回初始值零变化 ✓）。正解 = `perspective()` + `rotateY` + `transform-origin`（= 消失点 ✓）⇒ 远半收缩下沉、近半扩张浮起 ✓。**糊与角度无关** ✓ —— 糊因是**布局比画面宽**（见第 2 条 ✓）；**但"糊不糊"不能用包围盒比判定** ✗（见第 10 条 ✓）。
2. **绝不做"布局比画面宽"的补偿** ✗✗ —— 曾用 `width: calc(100% + 9.75rem)` 让布局 903 而绘制 719（**0.80× 压缩**）⇒ 满屏文字糊掉 ✓；用户原话"**卡片都很清晰，你现在非常模糊**" ✗。**角度不是糊的原因，布局↔绘制的比例才是** ✓。
3. **近边 1:1**：需要透视时，`transform-origin` 放**近边** ✓ 且**不加宽** ✓ —— 近边原样渲染 ⇒ 清晰 ✓。
4. **两张卡共享同一个变换** ✓ —— `.hero-tilt` **包住两者** ✓，小卡只在其上叠自己的 2D 旋转 ✓。一张有、一张没有 ⇒ 用户读成"**偏差感**" ✗。
5. **浮板 ∩ CTA 行 / 浮板 ∩ 标题 必须显式断言** ✓ —— 只查"浮板 ∩ 卡片"时，一次"文案居中"把按钮推到浮板底下**直接发货** ✗（用户："**你跟我说好了?**" ✓）。
6. **越界检查不排除任何元素** ✓ —— 曾把 `.hero-bloom` 从统计里排除 ✗，而**被切的正是它** ✓。
7. **装饰要么全幅、要么没有** ✓ —— 装饰层在 1200px 容器内用负 inset 越界 ⇒ 被 `overflow-x-clip` **硬切** ✗。
8. **深度的强弱 = `W ÷ (2·perspective)`，不是角度本身** ✓ —— 同一 `rotateY(9°)` 在宽 720px 与 1400px 上压缩比差一倍（5.8% vs 2.9% ✓）⇒ 角度调小＝深度直接消失 ✗。**现档**：`perspective(1200px) rotateY(-13°)` @ 783px 宽 ⇒ **左顶边低 36px、左右高度比 1:1.15** ✓（旧档 1800px 只有 25px 楔形，读不出深度 ✗）。其余仍**不许**：窗口下方单独加光带 ✗ · 垫底/泛光/自定义阴影 ✗（用户逐条否决 ✓）。
9. **暗色下卡片要有实边** ✓：祖先带 `transform` 时 `mask-composite` 描边环**不绘制** ✓（本仓实测两次 ✓）⇒ `.hero-plane` 作为祖先 ⇒ **暗色下必须给回退实边** ✓（`.dark .hero-plane [data-surface='card'] { border-color: color-mix(in oklab, var(--border), var(--foreground) 14%) }` ✓）。**实测对比度 = 1.88:1** ✗（`oklab(0.986…/0.2176)` 合成到 `rgb(11,12,16)` ⇒ ≈ `rgb(63,64,67)` ✓）—— **低于非文本 UI 的 3:1 门槛** ✓，卡片是装饰面故不构成违规 ✓，但这是已知的"边很淡"事实 ✓。
10. **"糊不糊"不能用包围盒比判定** ✗✗ —— 透视是**位置相关**投影：整卡绘/布比 `0.98` 看着没问题，**逐元素局部缩放却是 0.886 → 1.075** ✓ ⇒ 必须有**逐元素**读数（本仓口径：`getBoundingClientRect().width / offsetWidth` ✓）· **DPR=2 复核** ⇒ 读数不变 ✓（说明该口径与 DPR 无关 ✓）。

## 环境光路线（**已整体作废** ✗，如需重做请先读这段）

走过的四条路，全部被否：光带 → 4 枚椭圆斑 → 3 层合成光（各带 2–3 枚渐变、不同路径）→ 轨道光球（`rotate` 绕中心 + `scale` 拉伸 + `opacity` 呼吸；参考 LukyVj「glowing shadows」的手法 ✓）。
**留下的教训** ✓（重做时仍然适用）：
- 用**少数几层、每层多枚渐变**读成"一片光"，**不要**摆若干**可数**的椭圆 ✗（眼睛会数形状、会看出网格 ✓）。
- **不给动画元素加 `filter: blur()`** ✗ —— 本仓实测"模糊圆心每帧变 ⇒ 每帧重算" ✓；柔度用**渐变停靠点** ✓。
- 只动 **`transform` / `opacity`** ✓；动画放在 `@media (prefers-reduced-motion: no-preference)` 内 ✓ ⇒ 减动效下**光仍在、只是静止** ✓。
- 光层 `top` 至少比顶边低**一个漂移振幅** ✓（顶栏 `bg-background/90` + 模糊 ⇒ 底下的光会**透上来** ✓ 用户抓过 ✗）。
- 色相循环 ✗：配色归 `DESIGN.md`；要"颜色游移"就用**两色错相**呼吸 ✓。

## 判"有没有 3D"：**只信几何，不信图** ✗✗

判读（含 1:1 裁图）**三次**都说"看不到透视/行是平的" ✗ —— 而客观量测是：chrome 条布局高 39px、包围盒高 77px ⇒ 顶边横跨下沉 **38px** ✓。
⇒ **规则**：取一个横贯元素，比它的 `offsetHeight` 与 `getBoundingClientRect().height` ✓（差值 = 斜率 ✓）；再看**布局宽 vs 绘制宽**（比例离 1 越远越糊 ✓）。**图像（尤其降采样图）不是几何证据** ✗。
